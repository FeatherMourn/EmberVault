0001# EmberVault Enshrouded Reverse-Engineering Roadmap 0002 0003## End goal 0004 0005Build a private EmberVault fork of ShroudForge and companion research tools that systematically map what Enshrouded represents, exposes, permits, and persists for local/private-world research. 0006 0007Every result is classified independently as **represented**, **readable**, **writable**, **persistent**, or **unknown**. Static schemas and historical pre-1.0 findings guide hypotheses but do not establish current-build support. 0008 0009## Gates 0010 0011Every capability follows: schema evidence -> read-only accessor -> live readback -> ownership/authority validation -> guarded reversible write, if supported -> persistence test on a backed-up copy. No write gate opens from static evidence alone. 0012 0013## Research stages 0014 00151. **Player context** â€” completed. Validated local-player accessor returns a generation-checked handle and metadata. 00162. **Runtime census foundation** â€” completed. Bounded independent workers, shared ECS snapshots, readiness retries, 0017 stable package identity, hot reload, versioned exports, and stale-entry-point detection are validated. 00183. **Inventory and equipment** â€” partial. Player context, `InventorySetup` links, 32 linked containers, generic category 0019 metadata, and the live eight-slot schema are readable. The 1.4.1 worker graph is versioned and independently bounded; 0020 the linked-entity diagnostic now separates entity resolution from component readability; 0021 item-instance IDs, PIDE ownership, equipment records, and persistent item fields remain unknown. The equipment-link 0022 worker is isolated with an eight-entity cap and its own 30-second timeout. The fresh 1.4.2 package confirms the 0023 current boundary: links are present, but no linked entity or item component is readable through the supported path. 00244. **Item editor foundation** â€” create a read-only catalog/editor preview with provenance and expected-value checks. 00255. **Guarded item edits** â€” test one field at a time in a private world with readback, rollback, and save isolation. 00266. **Appearance** â€” map character setup, presets, hair, facial hair, colors, body proportions, and scale. 00277. **Player state** â€” map health, stamina, mana, buffs, abilities, progression, unlocks, and status effects. 00288. **World and building state** â€” map ownership, placement, build limits, blueprints, voxel context, and permissions. 00299. **Loot and pickup** â€” map definitions, world drops, pickup actions, ownership, and inventory transfer paths. 003010. **Localization and resources** â€” expose validated resource and localization lookups with language-aware output. 003111. **Diagnostics and compatibility** â€” add readiness events, capability reports, provenance, conflict detection, version hashes, and update checks. 003212. **Tooling** â€” package a private editor and export/import workflows, with backups, dry runs, explicit scope, and audit logs. 0033 0034## Exclusions 0035 0036No memory injection, protection bypasses, multiplayer advantages, arbitrary native hooks, or unverified live/save edits. Save research is limited to backed-up copies until format, checksums, round trips, and rollback are proven. 0037 0038## Evidence gates 0039 0040For each domain, record: 0041 00421. Reflection/KFC schema and field paths. 00432. Supported API or fork accessor used. 00443. Bounded live read and exact export provenance. 00454. Ownership/authority and world-generation validation. 00465. Write support, if any, tested with one expected-value transaction. 00476. Readback, restoration, persistence, and failure behavior. 0048 0049## Current milestone 0050 0051The forked read-only local-player accessor is live and validated in a private world. The runtime worker system, hot 0052reload, readiness retries, stable package, shared snapshot cache, root/src package synchronization, versioned exports, 0053and transient nonempty-capture preservation are validated. The 1.4.1 export verifier passes, with 32 inventory links 0054and the current eight-slot reflection schema readable. Item-instance linkage, equipment links, and several player-state 0055components remain unresolved and are not promoted to editor writes until fresh evidence exists. Stage 3 is now 0056explicitly gated on a new supported linked-entity accessor; Stage 4 read-only catalog work may proceed independently. 0057 0058## Bot execution instructions 0059 0060The following instructions are operational requirements for any bot continuing this roadmap. 0061 0062### Global operating loop 0063 0064For every stage: 0065 00661. Inspect the current repository, fork revision, game build, loader version, enabled packages, and existing reports. 00672. Preserve user changes and never reset or overwrite unrelated work. 00683. Start with static reflection, KFC, cache, documentation, and historical evidence. 00694. Build the smallest bounded read-only probe that tests the exact known schema. 00705. Give each worker its own retry state, timeout, entity/field budget, export, and error status. 00716. Use the shared snapshot/cache where possible; invalidate it on world-generation changes. 00727. Record package ID, version, fork commit, game build, timestamps, source paths, and evidence level. 00738. Verify that the package is enabled and actually executed before interpreting an export. 00749. Never infer writability from representation or readability. 007510. Stop and request user action before any restart, private-world test, save-copy operation, or write test. 0076 0077### Stage 1 â€” Player context 0078 0079The bot must locate the supported local-player accessor, validate the returned entity ID, generation, sequence, and 0080world-generation relationship, and reject missing, stale, ambiguous, or invalid handles. It must not enumerate all 0081entities or expose native pointers. Completion requires a reproducible private-world read export. 0082 0083### Stage 2 â€” Runtime census foundation 0084 0085The bot must maintain independent workers for each domain, use bounded round-robin scheduling, retry transient runtime 0086readiness errors, and export worker status separately. It must verify hot reload with a matching reload result and keep 0087native/package changes distinct from Lua reloads. Completion requires one world launch completing workers without a 0088restart between them. 0089 0090### Stage 3 â€” Inventory and equipment 0091 0092The bot must begin with reflection and inventory relationship schemas. It must read only the local-player ownership 0093chain, inventory setup links, bounded inventory containers, slot references, equipment records, and resolved item 0094instances. It must export candidate IDs and per-field status, including unavailable and resolve-error states. It must 0095not guess ownership from a registry index or expose editor writes until player-to-item ownership is proven. 0096 0097### Stage 4 â€” Item editor foundation 0098 0099The bot must generate a read-only catalog from verified ItemInfo, recipe, balancing, and runtime evidence. Every field 0100must include source, path, type, evidence level, build, and editability state. The UI/data model must distinguish 0101definition fields from instance fields and display unknown values explicitly. No mutation control may be enabled yet. 0102 0103### Stage 5 â€” Guarded item edits 0104 0105The bot may proceed only after Stage 3 proves ownership and readback. It must require a private/local world, capture the 0106expected value, perform one field transaction, read the value back, compare it, restore the original value, and record 0107the result. It must abort on stale handles, ownership mismatch, unexpected values, failed readback, or rollback failure. 0108No bulk edits, save edits, multiplayer edits, or unverified persistence claims are allowed. 0109 0110### Stage 6 â€” Appearance 0111 0112The bot must map CharacterSetup, presets, hair, facial hair, colors, body proportions, scale, meshes, and attachments 0113through reflection first. It must separate preset-resource writes from live-player appearance ownership. A no-op write is 0114not evidence of player appearance control. Any future visible test requires a private world, backup, expected-value check, 0115readback, and restoration. 0116 0117### Stage 7 â€” Player state 0118 0119The bot must probe health, stamina, mana, attributes, buffs, abilities, level, durability, progression, unlocks, and 0120status effects using exact reflected types and the validated player/related-entity context. It must record each component 0121independently, including direct-player versus related-entity results. It must not promote a field to writable because a 0122balancing table or preset contains a similarly named value. 0123 0124### Stage 8 â€” World and building state 0125 0126The bot must map building ownership, placement rules, altar/build-zone limits, blueprint metadata, voxel context, and 0127permissions using bounded reads. It must keep world coordinates, entity IDs, and blueprint payloads scoped to the private 0128test and avoid entity dumps. Placement or deletion remains disabled until ownership, authority, rollback, and persistence 0129are independently proven. 0130 0131### Stage 9 â€” Loot and pickup 0132 0133The bot must correlate static loot definitions, world-drop entities, pickup actions, ownership, inventory transfer, and 0134item-instance creation. It must test definitions before live actions and keep action probes read-only unless a separate 0135explicit private-world transaction is approved. A readable pickup schema does not prove that a mod may spawn, transfer, 0136duplicate, or delete loot. 0137 0138### Stage 10 â€” Localization and resources 0139 0140The bot must identify resource IDs, language bundles, localization tags, key-to-text mappings, and runtime lookup APIs. 0141It must prefer the supported resource accessor or verified offline decoder and preserve language/build provenance. It must 0142not substitute debug names for localized names without labeling them as fallbacks. 0143 0144### Stage 11 â€” Diagnostics and compatibility 0145 0146The bot must emit capability states for represented, readable, writable, persistent, and unknown. It must record loader, 0147fork, game, KFC, reflection, package, and schema versions. It must detect stale packages, duplicate exports, loader 0148conflicts, ABI mismatches, readiness races, and changed field paths. Failed probes must remain visible and must not be 0149silently replaced by older successful output. 0150 0151### Stage 12 â€” Tooling 0152 0153The bot may assemble a private editor only from fields that have passed the appropriate gates. It must support dry-run 0154mode, provenance display, backups, expected-value checks, one-field transactions, readback, rollback, audit logs, and 0155explicit private-world scope. Import/export and save workflows must operate on copies and require format, checksum, 0156round-trip, and recovery validation before any original is considered. 0157 0158## Completion rule 0159 0160The roadmap is complete only when every stage has a current-build evidence record and every unresolved capability is 0161explicitly labeled unknown or unsupported. A complete roadmap does not imply that every field is writable; it means the 0162limits are mapped, reproducible, and safely documented. 0163
