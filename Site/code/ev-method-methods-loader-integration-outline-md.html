0001# Universal Loader Integration Outline 0002 0003## Purpose 0004 0005Extend EmberVault with a build-aware inventory and compatibility layer for 0006native DLL loaders and chainloaded mods. This document connects the existing 0007ShroudForge/EML research model to the native bootstrap problem without 0008rewriting either framework or modifying the live game installation. 0009 0010## Current boundary 0011 0012EmberVault already provides: 0013 0014- build and export provenance; 0015- ShroudForge and standard EML package conventions; 0016- read-only probe packages; 0017- capability and evidence records; 0018- adapter diagnostics; 0019- validation and safety rules. 0020 0021The missing layer is native loader metadata: entry-point DLLs, forwarded 0022exports, chainload order, framework ownership, dependencies, conflicts, and 0023observed initialization results. 0024 0025## Proposed repository additions 0026 0027```text 00281.0/ 0029 loaders/ 0030 loader-registry.json 0031 dll-inventory.schema.json 0032 compatibility-rules.json 0033 profiles/ 0034 client.json 0035 dedicated-server.json 0036 reports/ 0037 loader-inventory-YYYY-MM-DD.json 0038 loader-compatibility-YYYY-MM-DD.md 0039 loader-diagnostics-YYYY-MM-DD.json 0040 methods/ 0041 loader-evidence-method.md 0042``` 0043 0044Raw DLLs, private saves, and live installation copies remain outside the 0045repository. The repository stores hashes, metadata, observed behavior, and 0046safe references to local artifacts. 0047 0048## Native loader record 0049 0050Each loader or native mod should be represented by a record containing: 0051 0052```json 0053{ 0054 "id": "example-loader", 0055 "displayName": "Example Loader", 0056 "framework": "shroudforge", 0057 "artifact": "relative/path/to/example.dll", 0058 "sha256": "recorded-locally", 0059 "architecture": "x64", 0060 "entryPointDll": "dinput8.dll", 0061 "forwardedExports": [], 0062 "loadPhase": "deferred", 0063 "dependencies": [], 0064 "conflicts": [], 0065 "targets": ["client"], 0066 "gameBuildRange": ["39026384728"], 0067 "evidenceState": "observed", 0068 "sourceRecord": "research-record-id" 0069} 0070``` 0071 0072The hash identifies the observed artifact; it does not grant permission to 0073redistribute it or establish that it is safe. 0074 0075## Compatibility model 0076 0077Compatibility should be evaluated in layers: 0078 00791. **File compatibility** â€” architecture, required exports, file identity, 0080 and dependency presence. 00812. **Bootstrap compatibility** â€” whether one proxy can load the artifact and 0082 forward the required exports. 00833. **Framework compatibility** â€” whether EML, ShroudForge, or another loader 0084 recognizes and initializes it. 00854. **Runtime compatibility** â€” whether initialization completes without a 0086 crash, duplicate hook, repeated activation, or unsupported profile. 00875. **Feature compatibility** â€” whether the mod's advertised behavior actually 0088 works on the recorded game build. 0089 0090Passing an earlier layer must not promote a later layer automatically. 0091 0092## First inventory targets 0093 0094The current installation provides an initial test set: 0095 0096- ModLoader Proxy as the active `dinput8.dll` bootstrap; 0097- ShroudForge's preserved `dinput8.dll` as a forwarded target; 0098- EML's installed `dbghelp.dll` path; 0099- Creative Mode; 0100- XHL Area Harvest; 0101- XHL Enemy Difficulty Limits; 0102- M182 Panel; 0103- the ShroudForge-style `sf-*` and `embervault-*` packages. 0104 0105The first inventory should record the files and logs without changing their 0106names or load order. Shroudtopia must be treated as a first-class framework, 0107not merely as a generic DLL, because its loader and mod configuration have 0108their own semantics. 0109 0110## Evidence workflow 0111 0112For each native artifact: 0113 01141. Record the path, size, timestamp, hash, architecture, and version metadata. 01152. Record the required bootstrap filename and any known exports. 01163. Record the configured load order and forwarding target. 01174. Capture one clean launch log with the current game-build identity. 01185. Record loaded, skipped, repeated, and failed initialization events. 01196. Compare the result with the framework's package/runtime records. 01207. Keep unresolved conflicts as explicit findings rather than guessing. 0121 0122The live installation is evidence only. Experiments belong in a copied, 0123backed-up test profile. 0124 0125## Adapter design 0126 0127The universal manager should use thin adapters rather than rewriting existing 0128frameworks. Generic native DLLs are a first-day supported class, but they must 0129declare their requirements explicitly because they cannot rely on framework 0130metadata: 0131 0132- **Proxy adapter:** generates chainloader configuration and validates export 0133 forwarding. 0134- **ShroudForge adapter:** discovers ShroudForge packages and reads their 0135 manifests and runtime status. 0136- **EML adapter:** discovers standard EML packages and records EML-specific 0137 runtime limitations. 0138- **Shroudtopia adapter:** discovers `shroudtopia.dll`, its configuration, and 0139 its mod directory; records Shroudtopia-specific lifecycle, configuration, 0140 and compatibility behavior without assuming that Shroudtopia mods are 0141 interchangeable with EML or ShroudForge packages. 0142- **Generic DLL adapter:** handles native mods that expose no framework 0143 manifest through a required user-authored manifest containing the entry-point 0144 DLL, exports, load phase, dependencies, conflicts, target, and compatibility 0145 range. Generic DLLs receive the same inventory, validation, logging, and 0146 rollback treatment as framework-managed mods. 0147 0148Each adapter reports the same normalized status fields used by EmberVault's 0149capability matrix. 0150 0151## Initial implementation slices 0152 0153### Slice A â€” Static inventory 0154 0155Create schemas and a read-only scanner for DLL metadata, manifests, configs, 0156logs, hashes, and load-order references. No renaming or process attachment. 0157The scanner must support ShroudForge packages, EML packages, and generic DLL 0158manifests from the first implementation. 0159 0160### Slice B â€” Compatibility report 0161 0162Generate a report showing entry-point collisions, missing dependencies, 0163duplicate artifact identities, framework ownership, and suspicious load-order 0164relationships. 0165 0166### Slice C â€” Test-profile validator 0167 0168Validate a copied installation before launch: expected files, backups, 0169configuration syntax, architecture, and rollback materials. 0170 0171### Slice D â€” Runtime evidence importer 0172 0173Import proxy, EML, and ShroudForge logs into normalized observed events. Do not 0174claim that a DLL worked merely because it loaded. 0175 0176### Slice E â€” Manager integration 0177 0178Only after the preceding slices are stable, add enable/disable operations and 0179configuration generation against a user-selected test profile. 0180 0181## Acceptance criteria for the first milestone 0182 0183The first milestone is complete when EmberVault can produce a machine-readable 0184inventory that answers: 0185 0186- Which bootstrap DLL is active? 0187- Which framework owns each loaded artifact? 0188- Which DLLs require the same entry-point name? 0189- What does the proxy forward, and where? 0190- What load order is configured? 0191- Which dependencies and conflicts are declared or inferred? 0192- Which components loaded, skipped, repeated, or failed? 0193- Which claims are static, observed, verified, blocked, or unsupported? 0194- Which generic DLL requirements were declared by the user and which remain 0195 unknown? 0196 0197No live installation mutation is required for this milestone. 0198
